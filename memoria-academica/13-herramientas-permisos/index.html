13. Sistema de herramientas y permisos

2 min de lectura

#13.1 Herramientas tipadas

Cada herramienta es un objeto Tool con nombre, descripción, un modelo Pydantic para sus argumentos, un nivel de permiso, una función asíncrona y un timeout. El esquema JSON que recibe el modelo de lenguaje se genera a partir del modelo Pydantic, de modo que la validación y la descripción no pueden desincronizarse.

class OpenUrlArgs(BaseModel):
    url: str = Field(..., max_length=2000)

    @field_validator("url")
    @classmethod
    def _http_only(cls, v: str) -> str:
        p = urlparse(v)
        if p.scheme not in ("http", "https") or not p.netloc:
            raise ValueError("Solo se permiten URLs http(s) completas")
        return v

open_app lanza el ejecutable con subprocess.Popen([...], shell=False): el modelo elige un identificador de la lista blanca, nunca una ruta ni un comando. No existe ninguna herramienta de terminal libre.

#13.3 Niveles y política

Ver el diagrama de decisión del capítulo 5. La política (PermissionPolicy.decide) admite permisos ampliados por herramienta en config/permissions.yaml (auto, confirm, disabled), pero el nivel 3 siempre exige confirmación, aunque se marque como auto.

#13.4 Confirmaciones

Cuando una acción necesita confirmación:

  1. Se crea una fila en pending_actions con una vista previa legible (p. ej., "Archivar el recuerdo «X» (se mueve a 99-Archivo, no se borra)").
  2. El modelo recibe un texto explícito: ACCIÓN NO EJECUTADA TODAVÍA. Requiere confirmación…. Así no puede afirmar que la ha realizado.
  3. El usuario aprueba o rechaza con POST /api/actions/{id}. Cada acción se resuelve una sola vez.

#13.5 Auditoría

Cada decisión queda registrada en audit_log: herramienta desconocida, argumentos inválidos, denegación, pendiente, aprobada, rechazada, ejecutada, error o timeout. Se consulta en GET /api/audit.

#13.6 Pruebas

8 pruebas de permisos y 3 del agente cubren estos casos. Por ejemplo, el modelo falso "pide" ejecutar una herramienta inexistente run_shell con format c: y el sistema la deniega (test_unknown_tool_requested_by_model_is_denied).

Las pruebas REAL con OpenAI confirmaron el comportamiento con el modelo de verdad: herramienta permitida (P-009), acción de nivel 2 que queda pendiente y se aprueba sin poder reutilizar la aprobación (P-010, P-011), y creación de un issue de GitHub rechazada desde el centro de permisos de la interfaz (P-038). La batería OWASP (P-027) añade el peor caso: un modelo «engañado» por inyección de instrucciones que pide una acción sensible tampoco consigue ejecutarla sin aprobación.
