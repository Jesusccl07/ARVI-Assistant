    Decisiones tecnológicas (ADR)¶

    Cada decisión sigue el formato Architecture Decision Record: contexto, decisión, alternativas consideradas y consecuencias. Estado: Aceptada, Propuesta o Sustituida.

    ADR-001 — Arquitectura híbrida nativa en Windows¶

    • Estado: Aceptada (2026-11-12).
    • Contexto: el PC usa Windows 11; ARVI debe abrir aplicaciones, consultar procesos y leer archivos locales. Ya existen n8n en Docker y Obsidian nativo.
    • Decisión: backend Python ejecutado de forma nativa en Windows; n8n se mantiene en Docker; VoiceStudio como aplicación nativa local; frontend web servido por el backend y empaquetado con Tauri para escritorio.
    • Alternativas: backend en Docker (descartado: un contenedor no puede abrir VS Code ni controlar ventanas del anfitrión); backend en WSL (descartado: misma limitación y más complejidad de red).
    • Consecuencias: instalación reproducible con uv; el agente local tiene acceso real al sistema, por lo que el sistema de permisos se vuelve crítico (ver ADR-008).

    ADR-002 — Python + FastAPI para el backend¶

    • Contexto: el backend orquesta el LLM, la memoria, la voz y las herramientas; necesita HTTP, WebSockets, validación de datos y un ecosistema de IA maduro.
    • Decisión: Python 3.12 con FastAPI, Pydantic v2 y Uvicorn.
    • Justificación: el SDK oficial de OpenAI es de primera clase en Python; FastAPI genera OpenAPI automáticamente (requisito de documentación), soporta async y WebSockets de forma nativa, y Pydantic permite tipar los argumentos de cada herramienta.
    • Alternativas: Node.js/Express (ecosistema de IA local menor, sin validación tipada integrada); Django (más pesado, orientado a aplicaciones con ORM y plantillas).

    ADR-003 — OpenAI como "cerebro" tras una interfaz LLMProvider¶

    • Decisión: API oficial de OpenAI (Responses API con function calling y streaming), accedida solo a través de la interfaz LLMProvider. Modelo por defecto gpt-6-luna (0,10 $/0,50 $ por millón de tokens de entrada/salida, el vigente más barato con function calling), configurable con ARVI_LLM_MODEL. Sustituyó a gpt-6.1-terra (1 $/5 $) el 2026-11-12 para reducir costes durante el desarrollo.
    • Justificación: requisito del proyecto; la interfaz permite sustituir el proveedor o el modelo sin modificar el agente, y facilita pruebas con un proveedor falso (FakeLLMProvider).

    ADR-004 — Obsidian (Markdown + YAML) como memoria duradera y SQLite FTS5 como índice¶

    • Decisión: los recuerdos son archivos Markdown con front matter YAML en una bóveda dedicada ARVI-Memory, fuera de Git. SQLite FTS5 actúa como índice reconstruible.
    • Justificación: el usuario puede leer y editar su memoria con Obsidian; el formato es abierto y portable. FTS5 está incluido en el SQLite de Python y no requiere servicios externos.
    • Fuente de verdad: los archivos Markdown. El índice se puede borrar y regenerar (reindex).
    • Alternativas: base vectorial (Chroma, Qdrant): se pospone; solo se añadirá búsqueda semántica si se demuestra que mejora la recuperación.

    ADR-005 — SQLite para conversaciones, auditoría y metadatos¶

    • Justificación: sin servidor, un único archivo, transacciones ACID y suficiente para un único usuario. Se guarda en data/ (ignorado por Git).

    ADR-006 — VoiceStudio como motor de voz local, con proveedores intercambiables¶

    • Decisión: interfaces SpeechToTextProvider y TextToSpeechProvider. Implementación principal: VoiceStudio (local, sin coste por uso). Alternativa: OpenAI (de pago por uso).
    • Justificación: prioridad del usuario por la ejecución local y gratuita; VoiceStudio ofrece síntesis, clonación/diseño de voz y transcripción Whisper con una API local (127.0.0.1:3900).
    • Riesgos: sin GPU NVIDIA la latencia será mayor (se medirá); el modelo por defecto OmniVoice figura como no comercial, aceptable para uso académico y personal.

    ADR-007 — n8n existente como motor de automatizaciones¶

    • Decisión: reutilizar el contenedor n8n-local. ARVI lo invoca mediante webhooks autenticados (cabecera secreta) y la API pública (X-N8N-API-KEY) para listar y consultar ejecuciones. Los workflows de ARVI llevan el prefijo ARVI · y la etiqueta arvi.
    • Justificación: n8n ya estaba instalado; la lógica conversacional permanece en ARVI y n8n solo ejecuta flujos, de modo que ARVI sigue funcionando si n8n no está disponible.

    ADR-008 — Permisos de cuatro niveles validados en el backend¶

    • Decisión: cada herramienta declara un nivel (0 informativa, 1 reversible, 2 modificación, 3 sensible). El backend decide si se ejecuta, se pide confirmación o se rechaza. El modelo nunca ejecuta comandos arbitrarios.
    • Justificación: mitigación de prompt injection (OWASP LLM01) y de excessive agency (LLM06): la seguridad no puede depender de las instrucciones dadas al modelo.

    ADR-009 — React + TypeScript + Vite, PWA y Tauri 2¶

    • Estado: Aceptada. React, TypeScript, Vite y PWA implementados (Fases 4 y 8); Tauri aplazado (ADR-011).
    • Justificación: un único código de interfaz para escritorio (Tauri) y móvil (PWA). Tauri genera binarios mucho más ligeros que Electron porque usa WebView2, ya incluido en Windows 11.

    ADR-010 — uv como gestor del entorno Python¶

    • Justificación: crea el entorno virtual y resuelve dependencias de forma reproducible con un archivo de bloqueo (uv.lock), y es mucho más rápido que pip.

    ADR-011 — PWA instalable antes que Tauri¶

    • Fecha: 2026-11-12. Estado: Aceptada (decisión del alumno).
    • Contexto: Tauri necesita en Windows el compilador de C++ de Microsoft y el Windows SDK, que no están instalados: unos 2-3 GB de descarga. Una descarga parecida ya cortó otro servicio web que el alumno publica desde este equipo (INC-011).
    • Decisión: hacer primero la PWA. Sin descargas, ya permite instalar ARVI como aplicación con ventana propia e icono. Tauri queda pendiente para un momento de poco tráfico.
    • Consecuencias: por ahora ARVI no arranca el backend solo ni tiene icono en la bandeja del sistema. La interfaz es la misma, así que Tauri se podrá añadir después sin rehacer nada.

    ADR-012 — OAuth de Google sin librerías externas, con servidor temporal y DPAPI¶

    • Fecha: 2026-11-12. Estado: Aceptada.
    • Contexto: se necesita acceso a Calendar y Gmail en nombre del usuario. Las librerías oficiales (google-auth-oauthlib, google-api-python-client) añaden muchas dependencias para dos llamadas REST. Además, la documentación de Google para aplicaciones de escritorio solo garantiza redirecciones del tipo http://127.0.0.1:puerto, sin ruta.
    • Decisión:
    • Implementar el flujo con httpx: PKCE S256, state y un servidor temporal asyncio en un puerto aleatorio de 127.0.0.1 que atiende una sola autorización.
    • Guardar el refresh token cifrado con DPAPI mediante ctypes, sin dependencias nuevas.
    • Usar el token de grano fino de GitHub directamente con la API REST.
    • Alternativas descartadas:
    • Guardar el refresh token en .env: quedaría en claro.
    • keyring: sería una dependencia más con el mismo resultado en Windows.
    • Una ruta de retorno en la API de ARVI: sería una ruta pública sin token.
    • Consecuencias: hay más código propio que mantener, pero está cubierto por pruebas que usan el servidor temporal real. DPAPI solo existe en Windows; en la integración continua se usa un almacén en memoria.
